# GitHub FR：创建、更新与详设同步

适用于用户明确要求在 GitHub 提交或修改 Feature Request，以及处理该 FR 的完整性审核。FR 是需求提案，不是 Pull Request；不要因缩写相似创建代码 PR。

## 读取来源和仓库约定

- 确定目标仓库、需求来源和动作：草稿、创建、更新、同步或重提。已有 Issue URL 时读取最新标题、正文、标签、状态和评论，保留用户手工修改；不要基于聊天旧稿覆盖。
- 读取默认分支的 `.github/ISSUE_TEMPLATE/`，选择匹配语言的 Feature request 模板，核对标题前缀、必填字段、默认标签及表单说明。模板位置和字段名以仓库为准，不硬编码某个仓库的三段标题。
- 搜索同主题已有提案；命中时优先更新或关联，避免重复提交。若用户明确要求重新提，按下面的重提流程处理。
- 涉及审核失败、自动标签或类型识别时，再读相关 workflow 和脚本。模板、标题、GitHub issue type 字段和标签是不同机制；不要假定标题带 `[Feature]` 就会按功能请求检查。
- 详设来源先读最新正文；飞书读取使用可用的文档工具，遵循 `feishu.md`。私有文档链接不能替代公开 Issue 中必需的需求内容。

## 从详设整理 FR

用目标模板组织内容，按复杂度保留以下信息，不必照搬整篇详设：

- 问题、当前能力缺口、使用场景和预期价值；关联需求与规划。
- 期望能力、首期范围、后续扩展和方案取舍；多仓库各自职责、拟新增/修改/复用范围。
- 数据/版本来源、接口与状态流程、关键风险和控制；避免保留已否决方案的旧目录、配置或图示。
- 可执行测试及量化验收：分子分母、单位、边界、次数、聚合、正常失败与基础设施错误；将新增用例编号同步到需求追踪及执行顺序。
- 当前状态及证据缺口。明确区分计划环境、实际调研环境与已验证运行环境，不为通过机器人检查虚构Python、系统、工具版本或运行结果。
- 模板或检查器确实要求环境信息时，读取可获得的实际信息；尚未部署则明确写计划与未验证，必要信息无法取得时说明缺口。

评测项目涉及官方参考时，分别说明官方公布成绩、官方实现直接实测、适配路径实测；保持官方基线复现和适配一致性两套结论，不把直接路径成绩静默替换公布基线。Agent选型结论、运行时风险、归一化输出职责、测试门禁与详设一致。不得自动沿用其他项目的模型名称、任务数量或精度阈值。

## 写入与核验

优先使用当前环境的 GitHub 连接器；能力不足或集成权限不足时，可使用已经授权的 `gh`。先核实当前身份，不输出凭证；没有可用授权时保留本地 Markdown 并说明阻塞，不绕过权限或静默切换其他账户。

- **创建：**按模板标题及字段生成正文，并在创建时请求模板声明的标签。API/CLI 创建不保证像网页表单一样自动应用标签、模板元数据或 issue type；提交后必须回读。不要声称调用API就等于已通过网页表单提交。
- **更新：**只修改用户要求的字段；保留无关标签、指派、里程碑和状态。读取提交前的最新正文，与已准备稿比较，发现并发变更先合并。
- **调用失败：**明确错误时按原因处理；超时或响应不明确时先搜索/回读，确认是否已创建或更新，不能直接重试造成重复Issue。
- **核验：**比对远端标题、正文、状态和标签；正文比较可归一化CRLF/LF及末尾空白，不忽略实质差异。正文成功但标签失败属于部分完成。
- **交付：**返回实际Issue链接，简述变更、未验证项及权限限制。不要把“提交成功”写成“审核通过”。

使用CLI时将完整Markdown写入UTF-8文件，通过 `--body-file` 传入，避免转义破坏换行、反引号或变量。示意命令中的仓库、编号、标签和路径须替换为已核实值：

```bash
gh issue create --repo OWNER/REPO --title "TITLE" --body-file fr.md --label LABEL
gh issue edit NUMBER --repo OWNER/REPO --body-file fr.md
gh issue view NUMBER --repo OWNER/REPO --json title,body,labels,state
```

## 审核、标签和权限

用户要求触发机器人审核时，按仓库实际触发词发一条评论；无需每次普通更新都自动评论。如用户要求修复已失败的审核，可在实际修复后触发一次复审。使用最新审核评论或对应运行句柄观察结果，区分等待、通过、失败和执行错误。

三项COMPLETE但总状态FAIL时，先查看完整要求及脚本，不凭截图推断正文缺失。有些检查器只按标签识别类型，缺少 `feature`/`enhancement` 会把FR当Bug检查；这只是需核实的具体模式，不是所有仓库的规则。

- 根据模板核实应有标签并尝试设置，回读确认；创建时传入标签也可能未保留。
- 无标签权限时，不通过编造Bug复现信息迎合错误分类，不重建Issue期待自动获得权限，不自行修改目标仓库检查器。
- 仍可完成正文修改并保存稿件。已获准评论时可说明需要维护者处理的标签及原因；否则向用户报告所需动作。
- 同一未解决原因不循环触发机器人、不重复发评论，不手动伪造 `content_check_passed` 等机器人结论标签。

## 用户明确要求删除或重提

先备份最新正文及必要上下文。按当前模板创建新 FR，回读检查内容和元数据后，再执行用户明确要求的旧Issue处理，避免先删后创建失败。标签失败时说明新FR仍有元数据缺口，不继续盲目重提。

删除通常需要更高权限；失败不能宣称已删除。关闭也属于独立状态变更，只有用户授权删除/撤下/替换旧FR的意图涵盖退役旧提案时，才可将关闭并关联新FR作为替代；否则询问是否关闭。保留标题正文和可追溯链接，明确最终是删除、关闭还是仍打开。关闭/评论也可能触发仓库自动化，回读确认最终状态。
